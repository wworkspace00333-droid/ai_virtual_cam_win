## 1. Архитектура (кратко)

```
              ┌────────────── UI-поток Qt (превью ≤30 к/с, страницы, статус) ──────────────┐
OBS-плагин ──shm──► obs-shm-reader ─┐                                                     │
веб-камера ──DShow/MF──► capture-* ─┼─► LatestSlot (только свежий кадр) ─┬─► video-pipeline ─► компоновщик D3D11|CPU ─► vcam_writer ─shm─► vcam_dshow.dll (в процессе клиента)
тестовый сигнал ───────────────────┘                                    │          ▲                                          └─► vcam_mf.dll (Frame Server, сессия 0)
                                                                         └─► ai-engine (ONNX: CUDA→DirectML→CPU, YuNet) ─► ByteTrack ─┘ (рамки предсказываются на момент кадра)
watchdog: перезапускает video-pipeline / ai-engine / захват по сердцебиению; capture-supervisor: переподключение входа
```

Потоки: `capture-*` или `obs-shm-reader` (по одному), `capture-supervisor`, `video-pipeline`, `ai-engine`,
`video-<имя>` (по одному на видео-ассет), `watchdog`, `global-hotkeys`, `com-enum` (временный), фоновые потоки страниц
(импорт модели, бенчмарк, установка камеры). Между потоками — только `LatestSlot` (без очередей) и замки на статистике.

**Что из ТЗ уже есть (не переделывать, а доводить):**
- ✅ «Только свежий кадр», отдельные потоки захвата, ИИ и вывода (`LatestSlot`, `video_pipeline.py`, `engine.py`).
- ✅ ИИ не на каждом кадре: частота по режиму производительности, между запусками ByteTrack предсказывает рамки на момент
  кадра (`tracked_at`). Нет: динамического N по загрузке.
- ✅ Пассивная передача: ручная и автоматическая после 5 сбоев рендера подряд; сбой ИИ не останавливает вывод.
- ✅ Бенчмарк с FPS, задержкой avg/p95, CPU, памятью, JSON+Markdown (`benchmark.py`, `windows_pc_report.py`). Нет: загрузки GPU в бенчмарке.
- ✅ Профили с импортом/экспортом (`profile_bundle.py`), глобальные горячие клавиши, RU/EN.
- ✅ Деинсталлятор снимает обе камеры и плагин OBS (проверено вживую). Нет: автоматического теста чистоты реестра.
- ✅ Сетевого кода в приложении нет (единственный — загрузка YuNet в `scripts/convert_models.py`, инструмент разработчика).

## 2. Находки: надёжность и потоки

| # | Где | Что не так | Последствие | Важность |
|---|---|---|---|---|
| R1 | `ai/engine.py` `restart()` | Зависший поток «бросается» (join 1 с), затем `start()` делает `_stop.clear()`. Брошенный поток видит `_stop` снятым и **продолжает работать** рядом с новым: два потока ИИ обновляют один трекер, двойная нагрузка. У `video_pipeline` для этого есть счётчик поколений, у ИИ — нет. | после срабатывания watchdog — дрожание рамок, удвоенная загрузка GPU/CPU | 🟠 |
| R2 | `platform/win/capture.py` `stop()` | После `join(timeout=3)` захват закрывается (`mfcap_close` / `release`), даже если поток ещё жив (завис в обратном вызове или в `cap.read()` DirectShow). `mfcap_close` освобождает объект, который читает `mfcap_read` в другом потоке. Тот же сброс `_stop.clear()` при повторном старте. | обращение к освобождённой памяти в нативном коде → падение процесса (редко, при зависании) | 🟠 |
| R3 | `core/video_pipeline.py` `stop()` | `camera.close()` вызывается после `join(timeout=3)`, даже если поток вывода ещё внутри `camera.send()`. | редкое исключение/гонка при закрытии; данные в shm защищены seqlock | 🟡 |
| R4 | `vcs_mfcap.cpp` | `g_started++ == 0` и `MFStartup` не атомарны вместе (два одновременных `mfcap_open`); `CoInitializeEx` без парного `CoUninitialize`. | теоретическая гонка при старте; безвредная утечка счётчика COM | 🟡 |
| R5 | `vcs_d3d11.cpp` / `d3d11.py` | Нет явной обработки `DXGI_ERROR_DEVICE_REMOVED` (сброс драйвера, обновление драйвера, переключение видеокарт ноутбука). Ошибка ведёт к откату на CPU (это проверено тестом), но пересоздание устройства не проверено. | после сброса драйвера — CPU-компоновка до перезапуска программы | 🟠 (проверить на железе) |
| R6 | `vcam_writer.py` SDDL | Объект общей памяти разрешает чтение **Everyone** (`(A;;GR;;;WD)`). Через `\Sessions\<id>\BaseNamedObjects\…` его может открыть процесс другого пользователя той же машины и читать выход камеры. Нужны только владелец, LOCAL SERVICE и контейнеры приложений. | утечка видео между пользователями одного ПК | 🟠 (приватность) |
| R7 | `vcam_writer.py` | Нет проверки `ERROR_ALREADY_EXISTS`: если объект с этим именем заранее создал другой процесс сессии, приложение пишет в чужой объект с чужим DACL. | подмена/чтение кадров процессом той же сессии (модель угроз: вредонос уже у пользователя) | 🟡 |
| R8 | `vcam_frames.cpp` | ✅ Читатель проверяет `seq`, размеры ≤ 1920×1080 и `stride == w*4` до копирования — чтение за границы из shm невозможно. | — | ✅ |
| R9 | `platform/win/obs_shm.py` `stop()` | (найдено при исправлении R2) Тот же шаблон: вид общей памяти OBS снимался (`UnmapViewOfFile`), даже если поток чтения ещё копировал кадр. | нарушение доступа → процесс падает без исключения Python | 🟠 |

## 6. Предлагаемый порядок работ

Маленькие коммиты в `windows-port`, тесты перед каждым коммитом, отчёт после фазы.

1. **Фаза 1a — исправления надёжности (сразу, ~1 день):** R1 (поколения у ИИ), R2 (не закрывать захват при живом потоке;
   ссылка-удержание в `mfcap_read`), R3, R6 (DACL без Everyone, затем живая проверка MF и DirectShow), R7, R4. Тест на каждый.
2. **Фаза 1 — лицензии (блокирует релиз):** `LICENSE` (по ответу владельца) → `THIRD_PARTY_NOTICES.md` +
   `scripts/check_licenses.py` (сверка установленных пакетов и DLL сборки со списком разрешённых, падение на GPL/AGPL) →
   FFmpeg без GPL (L3): своя LGPL-сборка PyAV только с декодерами, либо декодирование видео через Media Foundation;
   выбор по результату пробы → YOLO как отдельная загружаемая модель, замена по умолчанию (по ответу владельца) →
   убрать `bus.jpg`/COCO из установщика (свои демо-картинки) → подпись в `build_installer_win.ps1` через переменные
   окружения → чистка `.coverage`, `.gitignore`, `git gc`; веса моделей — в GitHub Releases с SHA-256, загрузка в
   установщике или по кнопке (сетевой код — только под отдельным флагом и с записью в документации).
3. **Фаза 2 — CI и качество:** ruff, mypy (`vcstudio/platform`, `vcstudio/core`), pytest + покрытие, сборка нативных частей
   и установщика как артефакта на `windows-2025`; смоук регистрации камеры в CI (если образ позволит; иначе — явный пропуск
   с причиной); pre-commit, `CONTRIBUTING.md`.
4. **Фаза 4 — камера** (раньше фазы 3: от неё зависит пользовательский опыт): «обе камеры» по умолчанию на Windows 11,
   «Проверка камеры» и «Переустановить камеру» в приложении, тест чистоты реестра после удаления, общий режим MF
   (с SDK 26100), обработка R5.
5. **Фаза 3 — производительность и ИИ:** динамическая частота ИИ по загрузке, FP16 для DirectML, кэш сессий, автовыбор
   профиля при первом запуске, сегментация фона и размытие, загрузка GPU в бенчмарке, путь shm → текстура D3D11.
   Все цифры — только с `windows_pc_report.py` на реальном ПК.
5b. **Фаза 3b — детекция любых предметов (раздел 7):** интерфейсы и ONNX-экспорт OWLv2 + SAM 2.1 (+ MobileSAM) с тестами
   корректности на сервере → видеотрекер → CLIP-проверка → цель «текст / клик / образец» в ROI → удержание и плавное
   скрытие → набор из 20 видео и `docs/ACCURACY.md`. Скорость — только на GPU-ПК.
6. **Фаза 5 — продукт:** мастер первого запуска, трей и автозапуск, Windows Graphics Capture, «отправить диагностику»

## 7. Детекция любых предметов (открытая лексика) — оценка

Требование владельца: цель задаётся текстом, кликом или образцом; конвейер «детектор открытой лексики (редко) → маска →
видеотрекер (каждый кадр) → проверка класса»; только разрешающие лицензии; адаптивная частота детектора; удержание
подстановки 0,3–0,5 с при потере и плавное скрытие; отчёт о точности без дообучения.

**Лицензии кандидатов** (по репозиториям авторов; перед включением каждой модели — сверка файла LICENSE и карточки весов,
запись в `THIRD_PARTY_NOTICES.md`):

| Роль | Кандидат | Лицензия кода / весов | Замечание |
|---|---|---|---|
| Детектор по тексту | OWLv2 (Google, scenic / HF `google/owlv2-*`) | Apache-2.0 / Apache-2.0 | проще экспорт в ONNX, есть режим «образец-картинка» (image-guided) — закрывает пункт (в) |
| Детектор по тексту | Grounding DINO (IDEA-Research) | Apache-2.0 / Apache-2.0 | точнее на сложных фразах, но экспорт в ONNX труден (кастомные операторы), тяжелее |

| Проверка класса | OpenCLIP (ViT-B/32) / CLIP (OpenAI) | MIT / веса MIT (OpenAI), OpenCLIP — веса обучены на LAION (проверить условия набора) | — |

**Реалистичность (без выдуманных цифр):** это модели в десятки–сотни миллионов параметров. На этом сервере (CPU, 2 ядра)
можно проверить корректность, экспорт и точность, но не скорость: здесь детектор открытой лексики будет работать порядка
секунд на кадр, поэтому реальное время (≥ 30 к/с вывода, детектор раз в N кадров) проверяется только на GPU-ПК и вносится
в `HARDWARE_CHECKLIST.md`. Вывод камеры от скорости детектора не зависит уже сейчас (трекер + `LatestSlot`), поэтому
адаптивный режим «падает частота детектора, а не камеры» ложится на существующую архитектуру.

**Как встраивается:** новые интерфейсы `OpenVocabDetector`, `Segmenter`, `VideoTracker` (ONNX, CUDA/DirectML/CPU, FP16,
кэш оптимизированных моделей ORT) рядом с существующим `detect(frame, conf, iou)`; ROI получает тип цели
«текст / клик / образец»; удержание подстановки и плавное скрытие — в трекере и компоновщике (альфа слоя по времени
с момента потери). Отладочный показ рамки и маски — в превью.

**Проверка точности:** 20 коротких видео с разными предметами под свободной лицензией (свои съёмки или CC0/CC-BY с
указанием авторов), разметка масок для части кадров; метрики — IoU маски, доля кадров с верным предметом, ложные
срабатывания, дрожание центра (px), FPS; `scripts/eval_open_vocab.py` → `docs/ACCURACY.md`. Цифры CPU — с пометкой среды.
